# Uplift — working notes for Claude Code

Uplift is a mobile app for private habit challenges among friends and family
(screen time, reading, prayer, pushups, custom goals). Circles persist; challenges
are time-limited activities inside them. Every challenge has an admin who reviews
proof and can correct results, with a visible change history.

Read these before changing anything:

- `docs/UPLIFT_SPEC.md` — the functional specification (its visual section is superseded).
- `docs/DESIGN.md` — the current visual identity and component rules.
- `docs/DECISIONS.md` — every assumption and product decision made while building.
- `docs/BUILD_STATUS.md` — what is functional, demo-only, deferred, and what was verified.
- `AGENTS.md` — Expo-specific guidance generated by `create-expo-app`. Expo changes
  every SDK: read the installed package's types instead of trusting memory.

## Visual identity — do not revert

The purple-and-lime brand kit in the original specification was **rejected on
2026-11-10**. Never reintroduce `#885BFF`, `#6635D9`, `#F1EBFF`, `#B5FF69`, the
angular "U" symbol, an italic uppercase sports wordmark, Space Grotesk headings,
or an esports / fantasy-league look. A unit test (`tests/unit/contrast.test.ts`)
fails if those colors return to the tokens.

The approved direction is **"Crew"**: white backgrounds, warm paper surfaces, large
tight black headings, black selected states and primary actions, soft shadows on
floating white controls, generous spacing, and color reserved for people
(generated avatars), habits (soft emoji tiles) and states. Tokens live in
`src/theme/`. The two rejected alternatives stay reviewable at `/design-lab`.

## Product invariants (never break these)

1. **Screen time is never self-reported.** It needs a daily screenshot reviewed
   by an admin (or a genuinely implemented device connection, which does not
   exist yet). No "I did it" checkbox, no fake "Connect" button.
2. **Proof for a day cannot be submitted before that day has ended** in the
   challenge time zone. The deadline is noon on the following local date.
3. **Pending review never scores** and never turns into success or failure by
   itself. Standings change only after a review, override or valid self-report.
4. **Approving evidence ≠ meeting the target.** A verified screenshot showing
   150 minutes is a verified *failed* day for a 120-minute goal.
5. **Overrides say "Admin adjusted"** — never "Screenshot verified" or "Device
   verified" — and always carry a reason. An admin reviewing their own proof is
   labeled "Admin self-reviewed".
6. **Every correction is audited** (actor, participant, date, old → new value /
   outcome, reason, time) in the same transaction as the change. Audit events are
   append-only for clients. History is never silently rewritten.
7. **The client is never trusted** for approval, outcome, reviewer, score,
   identity, lifecycle transitions or payment state. All writes go through
   server functions that derive identity from the session. RLS is on for every table.
8. **Evidence is private** to the participant and assigned challenge admins.
   Private bucket, short-lived signed URLs, never posted to chat, never logged.
9. **No money moves.** No-reward challenges are the product. Sponsor / shared-pot
   screens are demo previews labeled "Demo reward — no money collected"; live
   reward modes do not exist in the schema and the server refuses previews unless
   a server-side demo flag is on. Fees shown are "Illustrative fee, not final pricing".
10. **Never fabricate** payments, device connections, delivered push
    notifications, or test results. Unavailable features are hidden or disabled
    with an explanation.
11. **One time zone per published challenge**, immutable. Dates are `YYYY-MM-DD`
    keys in that zone; timestamps are UTC. Never add 24h of milliseconds to move a day.
12. **Demo Mode is visibly labeled** on every screen and never touches a real backend.

## Architecture

```
src/app/         Expo Router routes (thin: each file renders a feature screen)
src/features/    Screens and feature logic (auth, circles, challenges, checkins, ...)
src/components/  Shared UI primitives (the design system)
src/theme/       Tokens, typography, contrast helpers
src/domain/      PURE rules: time zones, scoring, lifecycle, rewards, errors. No React/Expo imports (lint-enforced).
src/data/        Repository interface, DTO schemas, SupabaseRepository, DemoRepository, query hooks
src/lib/         Validated config, Supabase client, storage, logging
supabase/        config, ordered migrations (schema, RLS, functions), seed, database tests
tests/           unit (domain), demo (repository contract on demo data), integration (same contract on local Supabase)
e2e/             Playwright flows against the web build
```

- `Repository` (in `src/data/repository.ts`) is the only way screens touch data.
  `SupabaseRepository` calls server functions; `DemoRepository` is an in-memory
  implementation over deterministic fixtures. **Both use `src/domain`** — do not
  write a second set of rules for the demo.
- The same contract test suite runs against both repositories.
- Server functions are `SECURITY DEFINER` with `search_path = ''`, check
  membership/role themselves, and raise an error code from
  `src/domain/errors.ts` as the exception message.
- Sensitive edits use optimistic concurrency (`expected_revision`); retries use
  idempotency keys. Do not silently retry non-idempotent operations.

## Commands

```bash
npm run web:demo        # Demo Mode in a browser (no backend)
npm run start:demo      # Demo Mode on a device / simulator
npm start               # Real backend (needs .env, see README)

npm run db:start        # local Supabase stack (Docker)
npm run db:reset        # apply migrations + seed
npm run db:env          # write local URL + publishable key into .env

npm run lint
npm run typecheck
npm test                # unit + demo contract tests (no backend needed)
npm run test:db         # database/authorization + integration tests (needs db:start)
npm run e2e:web         # Playwright flows against the web build
npm run check           # lint + typecheck + unit
```

`npx expo install` contacts Expo's API. If the network blocks it, prefix with
`EXPO_OFFLINE=1` to resolve versions from the bundled compatibility map.

Run lint, typecheck and tests before calling any task done, and say exactly
which checks could not run and why. Update `docs/BUILD_STATUS.md` and
`docs/DECISIONS.md` whenever behavior or scope changes.
